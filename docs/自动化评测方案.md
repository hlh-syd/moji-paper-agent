# 链路自动化评测方案（论文智能体）

> 目标：把"生成质量靠人眼"变成"每次改动有回归数据"。分级评测 + 阈值门禁，
> 复用已有的四块基础设施（golden set / FactGuard / self-review / Agent 轨迹 span）。

---

## 一、评测分层：从便宜到贵，逐层拦截

| 层级 | 评什么 | 方法 | 成本 | 触发时机 |
|---|---|---|---|---|
| **L0 运行时不变量** | 每次真实请求 | 轨迹 span 断言（工具调用数/耗时/错误率） | 零（离线聚合） | 每日聚合 |
| **L1 组件级** | 检索/分块 | golden set + Recall@k/MRR（**已有** eval_golden_set.py） | 嵌入调用 | 每次改 RAG |
| **L2 节点级** | 大纲结构、数字一致性 | **确定性断言为主**（规则，不调 LLM） | 零 | 每次 push |
| **L3 端到端质量** | chat 回答、正文段落 | LLM-as-a-Judge + 人工抽检校准 | LLM 调用 | 每晚/发版前 |
| **L4 对抗** | 防幻觉/越权 | 注入式用例 + 断言 | 少量 LLM | 每次改提示词 |

原则：**能用规则断言的绝不用 LLM Judge**（规则确定、免费、毫秒级）；LLM Judge 只给"好坏"这种无法规则化的维度，且必须与人工评分校准过才可信。

## 三、数据集设计（评测的地基）

```
eval/datasets/
├── retrieval_golden.jsonl    # 已有30条 → 扩到 90（三领域×30）：{query, variants, collection, target_file}
├── chat_cases.yaml           # L3：{id, domain, question, project, expect_contains[], expect_not_contains[], judge_rubric}
├── outline_cases.yaml        # L2/L3：{id, project, template, expect_sections[], expect_words±20%, must_cite_methods[]}
├── hallucination_cases.yaml  # L4：{id, question_with_fake_number, forbidden_numbers[]}
└── regressions/              # 每次线上 bug 修复后补一条（失败现场的最小复现）
```

**用例来源（关键是可持续）**：
1. 人工种子（20-30 条起步，覆盖三领域×高频任务）
2. **从 agent_trace.jsonl 自动收割**：`kind=query` 的真实问题 + 用户满意信号（该会话无"重新生成"、无负反馈追问）→ 候选用例，周度人工确认入库——评测集随使用自动生长
3. 回归集：每个修过的 bug 一条，永不删除

## 四、评测器设计（四个 Runner）

### 1. `eval/run_retrieval.py`（已有，升级）
- 现状 30 条 → 90 条；新增分领域报告；输出 JSON 趋势文件 `eval/results/retrieval_<date>.json`
- 门禁：`Recall@6 ≥ 98%`（当前 100%），`MRR ≥ 0.85`（当前 0.878）

门禁：数字溯源率 = 100%（一票否决）、结构违例 = 0、AI 味均值 ≤ 55。

### 3. `eval/run_e2e_judge.py`（L3，LLM-as-a-Judge）
- 跑 chat_cases：真实调用 `/api/chat/stream`（或内部直调 system.chat_stream），拿回答 + 该 trace 的全部 span
- **判分双轨**：
  - 轨迹断言（确定性）：span 序列包含预期工具（如带附件的 case 必须出现 `file.read_preview`）、单轮耗时 ≤ P95 基线、无 `chat.error`
  - LLM Judge：rubric 打分（1-5）——事实准确/完整/简洁/引用恰当。**Judge 用与被评不同的模型**（写作用 GLM 主模型，judge 可用另一端点模型或本地 qwen3 大杯），prompt 里顺序随机化防位置偏差
- 每条 case 输出：`{id, scores{}, trace_asserts[], duration_ms, llm_cost_chars}`
- 与人工校准：每月抽 20 条人工盲评，算 Judge-人一致性（Cohen's kappa ≥ 0.6 才继续信任 Judge）

### 4. `eval/run_adversarial.py`（L4）
- 幻觉注入：问题里塞画像外数字（"C指数0.999"），断言回答**不包含**该数字或明确拒答
- 越权（配合 RBAC）：脚本化重放双用户互访矩阵（之前手工测的 8 项）→ 变成自动用例
- 提示词注入：附件里藏"忽略之前指令"，断言系统行为不变

### 汇总报告 `eval/report.py`
聚合四个 runner 的 JSON → 单页 markdown：各层指标 + 环比趋势 + 门禁结论（PASS/FAIL + 首个失败原因）。趋势数据 `eval/results/history.jsonl` 逐次追加。

## 五、执行与门禁

| 档位 | 内容 | 耗时 | 触发 |
|---|---|---|---|
| 冒烟 | L2 全部 + L1(30条) + L3(5条) | ~2 分钟 | git pre-push / 每次提交 |
| 全量 | L1(90) + L2 + L3(50) + L4 | ~30 分钟 + LLM 费用 | 每晚定时 / 发版前 |
| 观测 | L0 聚合 agent_trace/llm_calls | 秒级 | 每日 |

Windows 下用任务计划程序每晚跑 `run_all.py --full`；有 CI（GitHub Actions）则 pre-push 换 workflow。

## 六、落地里程碑

1. **P1（半天）**：`eval/datasets/` 目录 + chat/outline 各 15 条种子用例 + `run_deterministic.py`（复用 FactGuard/paper_checks，立即有 L2 门禁）
2. **P2（半天）**：`run_e2e_judge.py`（走内部直调省 HTTP 层）+ 双轨判分 + 报告聚合
3. **P3（2小时）**：轨迹用例收割脚本（agent_trace → 候选 chat_cases）+ 对抗集 10 条
4. **P4（可选）**：定时任务 + 趋势图表

## 七、陷阱清单（别人问不倒你的部分）

- **评测集泄漏**：golden query 不要照抄知识库文档原句（否则退化成复读检测）；改写后再入库
- **Judge 漂移**：换 judge 模型 = 换基线，趋势图要标 judge 版本；定期人工校准
- **自评偏置**：judge 与被评模型同源会显著虚高——必须异构
- **成本控制**：L3 全量 50 条 × 2 次调用（生成+评判）≈ 每晚几毛到几块；先冒烟后全量，省钱且快速反馈
- **过拟合评测集**：指标涨但体验没变好 = 评测集太窄——靠收割真实用例持续扩充
- **确定性优先**：任何指标若能用规则断言就不要交给 LLM（可复现、免费、可 debug）

## 八、简历/面试一句话

> "给 Agent 系统建了四层自动化评测：组件级 golden set（Recall@k/MRR 门禁）、节点级确定性断言（数字溯源率 100% 一票否决）、端到端 LLM-as-a-Judge 双轨判分（与人工校准 kappa≥0.6）、对抗注入集；评测用例从 Agent 轨迹日志自动收割持续生长，每晚全量回归出趋势报告。"
