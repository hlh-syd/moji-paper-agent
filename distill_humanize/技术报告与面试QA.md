# humanize-9b：中文学术文本「去AI味」蒸馏模型 — 全流程技术报告与面试 QA

> 项目：论文智能体（墨记）的 AI 检测与去AI味子系统
> 角色：独立完成调研、数据工程、训练、量化导出、部署与系统集成
> 简历一句话：基于 18000 条反向蒸馏对，QLoRA 微调 Qwen3.5-9B 构建中文学术去AI味模型，经 llama.cpp Q4_K_M 量化后以 Ollama 部署，接入检测驱动的闭环改写系统，启发式评分 45→14 且数字/引用零丢失。

---

## 第一部分：项目背景与目标

**问题**：LLM 生成的中文学术论文带有可被检测器（知网/维普/朱雀）识别的统计特征——套话模板、句长匀速、三联排比、对偶结构。需要让生成的论文在语义保真（数字/引用/术语零改动）的前提下"像人写的"。

**方案演进**（三条路线对比后选定）：
1. 规则引擎（套话黑名单 + 句长突发性统计）—— 快但只能消除表层特征
2. 商业 Humanizer API（QuillBot 等）—— 英文强中文弱、无免费 API、不可控 → 排除
3. **反向蒸馏专用模型**（选定）—— 用"AI味→人类原文"数据微调开源 LLM，学会句式骨架级重写

**最终架构**：三层闭环 —— 本地启发式体检（定位问题）→ 规则引擎轻扫 → **humanize-9b 蒸馏模型深改** → 规则补刀收尾，每层之间有锁字校验与分数择优，朱雀官方 API 做外部公证复检。

## 第二部分：全流程详解

### 阶段一：调研与选型
- 调研 GitHub：humanize-zh（首个中文降AIGC开源模型，SFT+DPO 三阶段训练，无 License）、anti-aigc-zh（按检测算法原理反制的规则库，MIT）、simple-aigc-detect（中文 BERT 检测器，MIT）
- 结论：官方 9B 版无小参数量变体、无商用许可 → **用其开源数据集自蒸馏**，效果可控且规避许可风险

### 阶段二：数据工程（18000 条训练对）
- 来源：`XiangJinYu/Qwen3.5-9B-Humanize-Dataset` 的 `v15_sft_18k.jsonl`
- 构造原理（反向蒸馏）：CSL 中文学术摘要（人类原文）→ 用 Qwen3.5-9B 改写成"AI味版本"→ 组成 `(input=AI味文本, output=人类原文)` 训练对，模型学**逆方向映射** P(人类改写 | AI味原文)
- 我的处理：
  - 转 Qwen chat 模板格式（system 注入改写铁律：数字/引用/术语一字不动、句式变换>同义词替换）
  - **发现并修复数据坑**：CSL 人类原文是半角标点（逗号/句号），直接训练会让模型学坏论文排版 → 正则规范化为全角（保护小数点/编号）
  - 去重 + 长度过滤，产出 18000 条 `data/train.jsonl`

### 阶段三：训练（云端 RTX 5090 32GB，租用约 4 小时）
| 项 | 配置 | 理由 |
|---|---|---|
| 方法 | QLoRA（基座 4bit NF4 双量化冻结 + LoRA 适配器） | 9B 全参微调需 ~72GB；QLoRA 显存 ~24GB 且保留基座知识 |
| LoRA | r=16, α=32, dropout=0.05, 目标=q/k/v/o/gate/up/down 全部 7 类线性投影 | 可训练参数 3300 万（0.81%），充分覆盖注意力与 FFN |
| 优化 | lr 1e-4 cosine + 预热，有效 batch 16（2×8 梯度累积），paged_adamw_8bit | 防显存尖峰；paged 优化器防 OOM |
| 精度 | bf16 计算（5090/Ada 原生支持）| P100 等老卡只支持 fp16，卡型适配是关键坑 |
| 序列 | seq_len 1024，**labels 只对 assistant 段计 loss**（system+user mask 为 -100） | 不浪费容量学复述输入 |
| 轮次 | 2 epoch（3375 步） | 原作者 0.8 epoch 即收敛，2 轮稳收防过拟合模板腔 |
| 结果 | ~3 小时训完，loss 2.4→1.x，每 epoch 存 adapter checkpoint（~112MB） |

### 阶段四：合并与导出
1. **合并**：`PeftModel.merge_and_unload()` 将 LoRA 权重并入基座（CPU fp16，~5 分钟）→ 完整 18.5GB 模型
2. **GGUF 转换**：`convert_hf_to_gguf.py --outtype f16 --no-mtp`
   - **关键坑**：旧版 llama.cpp 不支持 `qwen35` 新架构（混合 Mamba/SSM+注意力），转换丢掉全部 hybrid 层张量（427 vs 官方 883）→ 从 master 分支获取新版转换器
   - **MTP 坑**：config 含 `mtp_num_hidden_layers=1`，默认把 block_count 写成 33 但只导出 32 层张量 → 加载时校验 `blk.32.attn_norm.weight` 失败 → 用官方 `--no-mtp` 旗标排除投机层
3. **量化**：`llama-quantize --max-buffer-size 256MiB humanize-9b-f16.gguf humanize-9b-q4km.gguf Q4_K_M` → **5.3GB**（从 17.9GB 压缩 70%，质量损失极小）

### 阶段五：部署（Ollama）
- **坑**：Ollama 0.34 内核不支持 qwen35 → 升级 0.35.1
- **坑**：Ollama 内容寻址存储（blob 文件名=sha256）导致同名 create 不替换旧模型 → 删除旧 blob 干净重建
- 部署验证：6.2 tok/s（RTX 4060 8GB 笔记本），中文输出正常

### 阶段六：跨机器工程（SSH 自动化）
- 云实例无直传通道 → 自研**分块 base64 SSH 传输**（32KB/块 + 3 次重试 + md5 双端校验）
- 大文件回传：dd 按 4MB 块 + base64 + 增量 md5，5.3GB 传输 44 分钟零损坏
- 无卡模式（CPU-only 容器）内存被 cgroup 限到 2GB → 量化加 `--max-buffer-size 256MiB` 分块解决

### 阶段七：系统集成（安全护栏优先）
`src/local_humanize.py` 接入闭环，四重保护：
1. **锁字校验**：改写前后比对数字/统计量/引用标记 `[n]` 集合，丢失即弃用输出
2. **分数择优**：蒸馏输出与规则引擎输出比分数，取更低者
3. **熔断器**：Ollama 不可用/失败 → 10 分钟内跳过该引擎（不影响主流程）
4. **长度守卫**：输出 <50% 输入判定截断弃用

## 第五部分：面试 QA

### A. 方法与原理层

**Q1：什么是反向蒸馏？为什么不用正向 SFT？**
> 正向做法是收集"人类改写 AI 文本"的数据（需要高质量人工标注）；反向做法是利用现成的人类原文（CSL 学术摘要），用同一个教师模型把它"AI味化"，得到 (AI味, 人类原文) 配对——因为人类原文天然存在且免费，18000 条数据零标注成本。模型学的映射是 P(人类改写 | AI味原文)，即"知道 AI 怎么把人话改坏，就能学会倒着走回来"。数学上这是风格迁移的条件语言建模，本质是让输出分布从 LLM 的"概率最优模式"向人类写作分布偏移。

**Q2：为什么选 QLoRA 而不是全参微调或 LoRA？**
> 全参微调 9B 需要 ~72GB 显存（AdamW 状态是参数的数倍），单卡不可行。普通 LoRA 基座仍要 bf16 权重（18GB）+ 激活，勉强但浪费。QLoRA 把冻结基座量化到 4bit NF4（9B→~6GB），LoRA 部分保持 bf16 训练，显存降到 ~24GB 可用 24GB 的 5090，且双量化（double quant）再省 0.4bit/参数、paged optimizer 防显存尖峰。可训练参数只有 0.81%，但 LoRA 的低秩假设支持"风格改写"这类任务不需要更新全部知识。

**Q3：LoRA 的原理？r 和 alpha 怎么定？**
> 冻结原权重 W，学习增量 ΔW=BA，其中 B∈R^{d×r}、A∈R^{r×k}，r≪d。前向 h=Wx+BAx(α/r)。r=16 是 7B~14B 级别风格任务的常用值（r=8 偏简单任务，r=64 是代码等高复杂度）；alpha=2r 是稳定比例的经验值；dropout 0.05 防小数据过拟合。目标模块选了全部 7 类线性投影（q/k/v/o/gate/up/down）——只调 attention 会限制句式重组能力，FFN 的 gate/up 对中文表达的调整同样重要。

**Q4：为什么只对 assistant 段计 loss？**
> 训练目标是"给定 AI 味输入产出人类化改写"，system/user 段是条件而非目标。若对全序列计 loss，模型会浪费容量去学复述输入甚至生成指令文本，且稀释 assistant 段的梯度信号。实现上把 system+user 模板化后的 token labels 全部置 -100（CrossEntropy 的 ignore_index）。

**Q5：为什么 2 epoch？过拟合怎么判断？**
> 原作者 SFT 0.8 epoch（900 步）loss 即平台化，说明任务简单、数据冗余度高；过拟合的表征是模型死记训练对的改写模式、对未见文本泛化差。我取 2 epoch 平衡充分学习与泛化，并每 epoch 存 checkpoint 以便选优。更严格的做法是留出验证集看改写质量的退化点（当时受 8 小时租期约束做了工程取舍）。

**Q6：Q4_K_M 量化是什么？为什么选它？**
> K-quant 分块量化：把权重按超块分组，每组用二级尺度（super-block scale + per-block scale）量化到 ~4.5bit 均值；_M 是中等混合策略——对 perplexity 敏感的层（如 attention 部分）用更高精度。相比朴素 Q4_0 精度损失小得多，相比 Q8_0 体积减半。17.9GB f16 → 5.3GB（-70%），在消费级显卡上可跑 9B。

**Q7：GGUF 是什么？为什么不用 ONNX/TensorRT？**
> GGUF 是 llama.cpp 的单文件模型格式（权重+tokenizer+元数据），面向 CPU/GPU 混合推理，支持 K-quant。选它因为目标是 Ollama 本地部署（Ollama 底层就是 llama.cpp），且笔记本场景需要 CPU offload 灵活性；TensorRT 偏数据中心 GPU 部署，ONNX 生态对 LLM 的 K-quant 支持不成熟。

### B. 踩坑与排查层（面试最有区分度）

**Q8：转换后模型加载报 `blk.32.attn_norm.weight not found`，怎么排查？**
> 分层二分：①先用 gguf-py 读元数据，发现 `block_count=33` 但张量只有 32 层——config 里有 `mtp_num_hidden_layers=1`（多 token 预测/MTP 投机层），转换器把 block_count 扩到 33 却没有对应权重；②查新版 llama.cpp 的 qwen.py 转换器源码，找到官方开关 `--no-mtp`（排除 NextN 投机层，与官方 GGUF 发布一致）；③对照官方发布的 qwen3.5 GGUF 确认它根本没有 nextn 键。教训：转换器的默认行为要对照官方产物的元数据验证。

**Q9：还发现过什么转换问题？**
> 更隐蔽的一个：最初用 ghproxy 镜像 clone 的 llama.cpp 是**旧版本**，不认识 qwen35 这个新混合架构（Mamba/SSM+attention 混合，`full_attention_interval=4`）。转换"成功"但输出只有 427 个张量（官方 9B 是 883）——线性注意力层的 SSM 权重全被静默丢弃。这类问题的危险在于**不报错只丢层**，模型能加载但行为退化。排查方法是拿官方发布的同架构 GGUF 做张量数量/名称对照。

**Q10：跨机器传输 5.3GB 模型怎么保证完整性？**
> 云实例 SSH 网关对 SFTP 和大流量通道都有限制。方案：上传用 32KB 分块 base64 内嵌命令 + 3 次重试（6.6MB 包）；下载用 `dd bs=4M skip=N` 分块 + base64 回传 + **双端 md5 校验**（本地 ea1d88…= 远端 ea1d88…），44 分钟零损坏。教训：先探测通道的尺寸上限（64KB 命令 OK 但大流量断连），再定分块策略。

**Q11：无卡模式（CPU 容器）量化为什么失败？怎么解决？**
> cgroup 把容器内存限到 2GB，llama-quantize 读第一个 2GB 的 f16 张量就 OOM 被杀（`cc1plus: Killed signal`，编译 -j4 也一样）。解法：量化器加 `--max-buffer-size 256MiB` 分块缓冲（正是为低内存设计的参数）+ 编译降 -j2 + 顺序执行避免转换与编译抢内存。

**Q12：Ollama 部署的坑？**
> ①0.34 内核不支持 qwen35 架构（`check_tensor_dims` 报错），升级 0.35.1；②内容寻址存储：blob 文件名=内容 sha256，同名 `ollama create` 如果 layer digest 没变不会替换文件——我手动覆盖旧 blob 后又被 create 流程恢复，最终以 `ollama rm` + 干净 Modelfile 重建解决。教训：内容寻址系统的"更新"语义和直觉不同，要用删除+重建保证干净状态。

### C. 系统设计层

**Q13：蒸馏模型怎么和现有系统集成？为什么不用它做第一轮改写？**
> 三层闭环：启发式体检（毫秒级定位具体套话/节奏问题）→ 规则引擎轻扫（命中句定向修复）→ **分数仍 >55 才调蒸馏模型深改** → 规则补刀。蒸馏模型不放第一轮因为：①推理成本高（6 tok/s，一节万字要分钟级），规则引擎毫秒级；②多数文本规则一轮就达标（68→9），模型只处理规则盲区（无套话但句式均匀的文本），按需触发省时省电。

**Q14：怎么保证改写不丢数字/引用这些事实要素？**
> 三重防线：①改写 prompt 的 system 段注入"数字/引用/术语一字不动"铁律；②**锁字校验**——正则提取改写前后的小数/整数/引用标记 `[n]` 集合，改写后集合必须包含前集合，丢失即弃用整个输出；③**分数择优**——蒸馏输出与原文本分别体检，只有分数更低才采纳，否则回退。宁可少改，绝不丢数据。

**Q15：Ollama 挂了会怎样？**
> 熔断器模式：`local_humanize.available()` 先查 `/api/tags` 确认模型在位；任何调用失败置 10 分钟熔断窗口，期间闭环直接跳到规则补刀轮。这来自本项目真实事故的教训——同步 Ollama 嵌入调用 502 重试曾把 FastAPI 事件循环拖死，此后所有本地推理调用都走 `asyncio.to_thread` + 超时 + 熔断。

**Q16：怎么评估这个模型的好坏？**
> 三个维度：①**检测器视角**（金标准）——朱雀官方 API 改写前后 AI 确证占比对比，自建文本 45 分降到检测认定的"人类写作"；②**保真视角**——锁字校验通过率（数字/引用零丢失）+ difflib 相似度（套话文本 77% 深改 vs 正常文本 98.6% 保守，符合预期行为模式）；③**启发式评分**——本地体检器的套话/节奏指标前后对比。改进方向：人评 + 更大的留出测试集。

### D. 开放与深挖题

**Q17：如果重新做一次，你会改什么？**
> ①先拉官方发布的 GGUF 对照元数据再转换（省掉 3 轮排障）；②训练前留出 500 条验证集监控过拟合；③上 DPO 阶段——数据集里现成有 5500 条 formal/casual rejected 对，能修正"越口语化越好"的偏差；④训练机先跑冒烟再启动全量，当时是冒烟通过但 18 小时长跑的散热问题没预估。

**Q18：这个模型有什么局限？**
> ①SFT-only，没有 DPO 对齐，偶尔改写不够彻底（对正常文本 98.6% 保守）；②训练数据是 CSL 摘要文体，对非摘要文体（方法细节、讨论）泛化未验证；③无 License 的上游数据，只能个人研究用；④Q4 量化在极端长句上有轻微退化。

**Q19：为什么最后你的论文不需要这个模型？（考察诚实度）**
> 因为整套预防体系生效了——写作宪法预置反模板规则、每节生成后自动体检去AI味、八层反制规则吸收进改写指南，最终全文朱雀 AI 确证占比 1~3.7%、本地 BERT 0%。蒸馏模型是为"规则盲区"准备的保险，这正是系统该有的状态：能力冗余但按需触发。

**Q20：Qwen3.5 是混合架构（SSM+Attention），这对部署有什么影响？**
> 32 层中每 4 层才有 1 层全注意力，其余是线性注意力（Mamba 式 SSM，conv1d + state space 参数）。影响：①转换器必须识别 `layer_types` 和 `ssm.*` 张量，旧版会静默丢弃；②推理时 SSM 状态显存占用与序列长度无关，长文本显存友好；③K-quant 对 SSM 的小张量（如 `ssm_a`）敏感性更高，量化后需重点回归测试长文本一致性。
